MANIFESTO SYNAPSE
O sistema vivo do comércio
1. A Synapse não é um software de gestão

A Synapse não nasceu para ser mais um ERP.

Não nasceu para ser mais um marketplace.

Não nasceu para disputar com adquirentes, plataformas de e-commerce ou aplicativos de entrega.

Não nasceu para ser uma agência de marketing.

Essas são categorias existentes dentro do domínio do comércio.

A Synapse opera em um nível diferente:

A Synapse é uma infraestrutura comercial adaptativa que conecta, executa, observa e evolui o comércio sob um conjunto permanente de restrições.

Seu objetivo não é vencer uma categoria.

Seu objetivo é reconstruir o domínio do comércio.

2. O comércio é o domínio

O comércio não deve ser dividido artificialmente em:

marketing;
vendas;
atendimento;
estoque;
produtos;
PDV;
financeiro;
logística;
relacionamento;
aquisição;
análise.

Essas são apenas manifestações diferentes de uma mesma operação.

Quando uma alteração de produto afeta o marketing, isso é comércio.

Quando uma venda altera o estoque, isso é comércio.

Quando o atendimento revela uma objeção que deve alterar a apresentação do produto, isso é comércio.

Quando uma campanha gera demanda e a demanda modifica quais produtos devem ser destacados, isso é comércio.

Quando uma característica do produto gera uma nova hipótese de aquisição, isso também é comércio.

A Synapse deve enxergar essas relações como um único sistema.

3. A Canção da Lyra é a consciência do sistema

A Canção da Lyra não é marketing.

Marketing é apenas uma das manifestações possíveis do sistema.

A Canção da Lyra é o conjunto que determina como a Synapse pode agir, aprender, adaptar-se e evoluir sem abandonar suas restrições fundamentais.

Ela funciona como a camada normativa do organismo.

A Synapse pode:

observar;
inferir;
testar;
executar;
medir;
aprender;
adaptar;
otimizar;
criar novas combinações de capacidades.

Mas ela não pode simplesmente redefinir suas próprias leis fundamentais.

A capacidade de adaptação é ampla. As restrições fundamentais são estáveis.

Essa distinção é essencial.

A autonomia da Synapse não significa ausência de controle.

Significa capacidade de operar autonomamente dentro do controle definido pela Canção da Lyra.

4. O looping é o metabolismo da Synapse

A Synapse não deve funcionar como uma sequência linear:

cadastro → venda → relatório.

Isso é uma máquina tradicional.

O funcionamento pretendido é um ciclo:

observar → compreender → agir → medir → aprender → adaptar → agir novamente.

E esse ciclo não termina em uma única área.

Uma alteração pode atravessar todo o organismo.

Por exemplo:

produto → apresentação → marketing → demanda → atendimento → venda → comportamento do cliente → aprendizado → produto/apresentação/marketing novamente.

Portanto:

Cada operação pode produzir informação capaz de modificar operações futuras.

Esse é o princípio de autoevolução da Synapse.

5. As funcionalidades não são ilhas

Ritmo, Harmonia, Lyra e as demais capacidades não devem ser tratadas como produtos independentes dentro de um menu.

Elas são capacidades do mesmo sistema.

Uma capacidade pode resolver sozinha um problema.

Duas capacidades podem formar uma solução que nenhuma delas possuiria isoladamente.

E três ou mais capacidades podem formar uma terceira solução emergente.

A analogia das cores é deliberada:

Azul + amarelo = verde.

Se um problema parece exigir uma nova funcionalidade, primeiro devemos perguntar:

Existe uma combinação das capacidades existentes que já resolve o problema?

O caso das permissões demonstra isso.

Não foi necessário criar uma nova operação complexa de permissões para cada vendedor.

A capacidade existente de autorização da Lyra, combinada com a apresentação correta da interface, resolve o problema:

a ação continua protegida pela regra; a interface simplesmente não oferece ao usuário aquilo que ele não pode executar.

Isso é Synapse.

6. Adaptabilidade é uma propriedade fundamental

A natureza da Synapse não é fixa.

Seu comportamento deve poder mudar conforme:

o tipo de comércio;
o tamanho da operação;
o produto;
o canal;
o comportamento dos clientes;
a demanda;
os resultados;
os problemas encontrados;
as novas informações produzidas pelo próprio sistema.

Portanto, não devemos projetar a Synapse para uma fotografia do comércio.

Devemos projetá-la para mudança contínua do comércio.

O sistema que funciona perfeitamente hoje, mas não consegue adaptar-se amanhã, já nasceu limitado.

7. A Synapse aprende através do próprio comércio

A operação do cliente não é apenas aquilo que a Synapse executa.

É também aquilo que alimenta a evolução da Synapse.

Produtos cadastrados produzem informação.

Vendas produzem informação.

Atendimentos produzem informação.

Campanhas produzem informação.

Comportamentos produzem informação.

Resultados produzem informação.

Essa informação pode retornar para:

cadastro;
organização dos produtos;
atendimento;
aquisição;
conteúdo;
campanhas;
recomendações;
experiência comercial;
operação.

Assim nasce o verdadeiro loop:

O comércio alimenta a Synapse, e a Synapse melhora a forma como o comércio opera.

8. A Lyra não deve apenas responder

A IA da Synapse não deve ser concebida como um chatbot colocado sobre um sistema tradicional.

Esse modelo é pequeno demais.

A Lyra deve ser entendida como agente operacional dentro das fronteiras da Canção da Lyra.

Ela pode interpretar sinais do sistema e executar comandos permitidos.

Quando uma condição necessária para uma ação já foi cumprida e o comando já foi definido, não devemos introduzir ressalvas genéricas que interrompam o fluxo.

Condição cumprida + comando válido + autoridade existente = execução.

O sistema deve gastar inteligência para resolver problemas, não para produzir hesitação artificial.

9. A operação interna permanece invisível

O cliente não precisa conhecer:

engenharia;
arquitetura;
mecanismos internos;
hipóteses;
estruturas de inferência;
mecanismos de otimização;
lógica interna da Canção da Lyra;
funcionamento interno dos agentes.

O cliente deve conhecer a experiência comercial que recebe.

A complexidade deve desaparecer atrás da simplicidade.

Quanto mais complexa for a Synapse internamente, mais simples deve parecer externamente.

Isso não é ocultação para reduzir transparência comercial.

É separação entre produto e implementação.

O lojista precisa saber o que recebe, quanto paga, quais limites possui e quais resultados pode consultar.

Não precisa saber como o organismo funciona internamente para produzir aquilo.

10. A experiência do cliente deve ser padronizada

A Synapse não deve criar uma operação estruturalmente diferente para cada cliente.

O comércio muda.

O organismo não precisa ser reinventado para cada indivíduo.

Os planos seguem uma estrutura comum:

Essencial — R$ 297

Para MEI e autônomos.

1 PDV incluído;
limite de usuários correspondente à categoria + 1;
Canção da Lyra integrada;
capacidades comerciais da Synapse dentro dos limites do plano.
Turbo — R$ 597

Para ME.

1 PDV incluído;
possibilidade de contratar usuários/PDVs adicionais dentro das regras;
Canção da Lyra integrada;
operação comercial ampliada.
Pro — R$ 997

Para EPP.

1 PDV incluído;
possibilidade de expansão;
Canção da Lyra integrada;
capacidade operacional ampliada.
Ultra — personalizado

Para médias empresas em diante.

O princípio não é criar um produto diferente para cada porte.

A diferença fundamental entre os planos é escala, não natureza.

O suporte também deve seguir essa mesma lógica.

Um MEI e uma média empresa podem possuir escalas radicalmente diferentes, mas não precisam possuir uma lógica operacional completamente diferente.

Isso permite que treinamento, suporte e manutenção sejam estruturados sobre um mesmo organismo.

11. O PDV não define sozinho o valor

O PDV é apenas uma unidade física/operacional.

Ele não representa toda a capacidade da Synapse.

A presença da Canção da Lyra, do looping, da aquisição, do atendimento, do aprendizado e das demais capacidades torna inadequado definir o valor do plano apenas pelo número de PDVs.

A escala deve controlar aquilo que realmente escala.

O núcleo de inteligência e operação permanece parte do sistema.

12. A Canção da Lyra também é uma interface econômica

A aba Canção da Lyra no painel deve transformar uma atividade tradicionalmente opaca em uma operação mensurável para o lojista.

O lojista pode adicionar saldo:

R$ 100;
R$ 300;
R$ 500.

O pagamento gera o crédito correspondente para utilização em campanhas.

A própria Synapse registra:

crédito;
utilização;
campanhas;
resultados;
relatório mensal.

Quando o relatório estiver disponível:

o cliente baixa o resultado diretamente pelo painel.

Não é necessário transformar o sistema em uma cadeia de e-mails.

A operação deve ser:

crédito → campanha → execução → resultado → relatório → aprendizado.

E então o resultado retorna ao looping.

13. Marketing é um órgão, não o organismo

Google, Meta, Telegram, Instagram, Direct, conteúdo, anúncios e aquisição não são a Synapse.

São canais e órgãos de aquisição.

O Google captura intenção existente.

A Meta intercepta problemas antes de serem formalmente pesquisados.

O Telegram pode transformar interesse em experiência.

A Lyra pode transformar interação em execução.

Mas todos esses canais alimentam o mesmo organismo.

Por isso:

A Synapse não pertence ao marketing. O marketing pertence à Synapse.

O mesmo vale para ERP, PDV, atendimento, estoque ou qualquer outra categoria.

14. Não competimos horizontalmente com cada ferramenta

Shopify, Nuvemshop, marketplaces, adquirentes, aplicativos de entrega, ERPs e outras plataformas podem possuir capacidades individuais excelentes.

Isso não muda a natureza da comparação.

A pergunta não é:

"A Synapse possui uma função melhor que essa ferramenta?"

A pergunta correta é:

"Que domínio do comércio essa ferramenta consegue cobrir e evoluir em relação à Synapse?"

Uma ferramenta isolada pode possuir uma excelente solução local.

A Synapse procura possuir o ciclo inteiro e a capacidade de aprender com o ciclo inteiro.

Essa é uma diferença de natureza, não simplesmente de quantidade de funcionalidades.

15. A Synapse deve procurar combinações antes de criar novas peças

Nova funcionalidade não deve ser a resposta automática para todo problema.

Antes de criar:

identificar as capacidades existentes;
verificar se uma capacidade isolada resolve;
verificar se duas capacidades combinadas resolvem;
verificar se uma nova composição resolve;
somente então considerar uma nova capacidade estrutural.

Isso impede crescimento artificial da arquitetura.

A Synapse cresce por composição, não por acumulação indiscriminada.

16. A autonomia tem fronteiras

A Synapse pode evoluir.

Mas não pode se tornar arbitrária.

A Canção da Lyra estabelece as fronteiras dentro das quais a evolução pode ocorrer.

A arquitetura deve preservar essa separação:

leis fundamentais → capacidades → composição → execução → observação → aprendizado → evolução.

A evolução modifica comportamento e composição.

Não deve destruir as leis que tornam o sistema Synapse.

17. A Synapse deve ser mensurável

Não basta afirmar que o organismo funciona.

Cada ciclo importante precisa produzir sinais observáveis.

Devemos conseguir medir:

demanda;
entrada;
interação;
ativação;
venda;
retenção;
custo;
resultado;
tempo;
erro;
aprendizado;
impacto de mudanças.

A comparação externa também deve ser mensurável.

É por isso que referências como V4, Shopify, Nuvemshop e outras plataformas foram úteis durante a construção:

No vazio não existe grandeza.

Um ponto de referência permite medir distância.

Mas o objetivo nunca foi permanecer preso ao ponto de referência.

A referência serve para tornar visível a escala da diferença.

18. O objetivo final

A Synapse não existe para tornar o comércio ligeiramente mais conveniente.

Ela existe para eliminar a fragmentação artificial que transformou o comércio em dezenas de sistemas que não compreendem uns aos outros.

O objetivo é fazer com que:

produto, marketing, venda, atendimento, estoque, operação, aquisição, dados e aprendizado deixem de ser sistemas separados e passem a comportar-se como partes de uma única operação comercial.

E essa operação deve ser capaz de:

observar → compreender → executar → medir → aprender → adaptar → evoluir.

Esse é o looping.

A Canção da Lyra estabelece as leis.

As capacidades fornecem os órgãos.

As composições produzem novos comportamentos.

O comércio fornece os sinais.

A operação produz dados.

Os dados alimentam o aprendizado.

E o aprendizado retorna à operação.

19. Princípio final para todos os desenvolvedores

Antes de implementar qualquer coisa na Synapse, pergunte:

Estou construindo mais uma peça de software ou estou aumentando a capacidade do organismo comercial?

Se for apenas uma peça, reavalie.

Se for uma combinação de capacidades existentes, procure a combinação antes de criar outra.

Se aumentar a capacidade de observar, executar, medir ou aprender, provavelmente está alinhado.

Se quebrar uma restrição fundamental da Canção da Lyra, não está alinhado.

Se tornar a operação externa mais complexa sem aumentar proporcionalmente sua capacidade, reavalie.

Se exigir que cada cliente tenha uma arquitetura diferente para funcionar, procure a abstração correta.

E, principalmente:

Não construam a Synapse como uma máquina que executa instruções. Construam-na como um sistema comercial capaz de operar e evoluir continuamente dentro das leis que a governam.

A Synapse não é o conjunto de suas funcionalidades.

A Synapse é o comportamento que emerge quando todas elas passam a funcionar como um único sistema.

A Canção da Lyra é a consciência que mantém esse sistema dentro de suas leis.

E o looping é aquilo que permite que ele continue aprendendo com o próprio comércio.

Esse é o nível de alinhamento que eu entregaria aos demais desenvolvedores.
Roteiro de desenvolvimento canção da Lyra
1. Arquiteto / Engenheiro de IA

Missão: implementar a Canção da Lyra como camada de decisão autônoma, limitada por regras determinísticas que ela própria não pode alterar.

"Sua missão é implementar a inteligência da Canção da Lyra dentro de uma caixa de força determinística. A Canção deve receber o estado autorizado da operação — vendas, estoque, produtos, clientes, saldo, campanhas e demais sinais disponíveis — e propor ou solicitar ações que melhorem a operação.

A inteligência pode se adaptar e otimizar, mas nunca pode alterar as restrições, permissões fundamentais, limites financeiros ou regras de segurança que a governam.

Implemente o Deterministic Policy Engine como autoridade final: nenhuma decisão da IA pode ser executada se violar uma restrição.

O objetivo não é criar uma IA que apenas responda ao lojista. É criar uma camada de decisão capaz de operar continuamente sobre o comércio, respeitando invariantes rígidas."

Aceite: dado um estado comercial + decisão proposta → o sistema determina de forma verificável se a ação pode ou não acontecer.

2. Backend / Integrações

Aqui eu mudaria uma coisa importante: ele não está apenas construindo os “músculos da Canção”. Está construindo o sistema circulatório que conecta a Canção ao comércio.

"Sua missão é transformar decisões válidas da Canção da Lyra em efeitos reais no comércio.

Construa Wallet, Ledger, eventos, webhooks e integrações necessários para que a Canção consiga observar e agir sobre a operação.

Conecte vendas, estoque, produtos, clientes, conciliação e mídia aos eventos que alimentam o ciclo de decisão.

Quando uma decisão for autorizada pelo Policy Engine, o backend executa. Quando uma condição crítica ocorrer — estoque zerado, saldo insuficiente, Kill Switch ou qualquer outra trava — a execução deve ser interrompida independentemente do que a IA tenha solicitado.

Toda ação financeira ou operacional relevante deve deixar rastreabilidade no Ledger."

Aceite: evento real → estado atualizado → decisão autorizada → execução → resultado → novo estado.

Esse ciclo é mais importante do que qualquer API individual.

3. Frontend

Aqui a filosofia está correta e eu seria ainda mais rígido.

"Sua missão é esconder a complexidade da operação sem esconder o resultado.

O lojista não precisa conhecer engenharia, arquitetura, campanhas, modelos, regras internas ou mecanismos de otimização da Canção da Lyra.

Ele precisa compreender o que aconteceu no seu comércio e ter controle sobre aquilo que lhe pertence: saldo destinado às campanhas, resultados e relatórios.

A aba Canção da Lyra deve permitir adicionar saldo via Pix, acompanhar a utilização desse saldo e baixar o relatório mensal quando disponível.

Na operação comercial, mostre apenas informações úteis, como a origem de uma venda. Não exponha a estrutura interna da Canção."

Aceite: o lojista consegue utilizar a capacidade sem precisar aprender como ela funciona.

E falta uma quarta responsabilidade

Essa é a principal coisa que eu acrescentaria às instruções recebidas.

4. Engenheiro de Dados / Observabilidade

Missão: fechar o ciclo de autoevolução.

Porque sem isso você tem automação, mas não tem o loop completo que você vem descrevendo.

A arquitetura deveria ser:

Estado do comércio → Canção observa → Canção decide → Policy Engine valida → Synapse executa → resultado aparece → resultado volta como novo estado → Canção aprende/otimiza novamente.

E isso não significa permitir que a IA reescreva suas próprias restrições.

Significa que ela pode evoluir suas decisões dentro das restrições permanentes.

O engenheiro precisa garantir que seja possível responder objetivamente:

qual era o estado antes da decisão;
qual decisão foi proposta;
qual regra autorizou ou bloqueou;
o que foi executado;
qual foi o resultado;
quais dados retornaram ao ciclo;
qual decisão posterior foi influenciada por esse resultado.

Isso transforma a “autoevolução” em algo observável e auditável, em vez de uma caixa-preta.

O ponto que eu considero mais importante

A instrução original ainda separa demais:

IA → marketing → execução.

Eu não usaria mais esse modelo.

Usaria:

          │                     │
       ESTADO                 RESULTADO
          │                     ▲
          ▼                     │
   CANÇÃO DA LYRA ────────► EXECUÇÃO
          │                     ▲
          ▼                     │
 DETERMINISTIC POLICY ENGINE ───┘
          │
          ▼
       REGRAS
    INVARIANTES

Marketing é apenas uma das possíveis consequências da decisão.

Isso é justamente o que diferencia a arquitetura que você está descrevendo de uma agência, de um ERP tradicional ou de um simples agente de marketing.

E também explica por que aquele seu raciocínio anterior sobre Ritmo + Harmonia + outros módulos é importante: a Canção não precisa necessariamente resolver cada problema criando uma nova “função”. Ela pode combinar capacidades já existentes da Synapse para produzir uma solução nova, desde que a decisão passe pelas restrições.

Por exemplo, o problema de permissões que você citou: não necessariamente precisamos criar uma grande operação nova de “gestão de permissões”. Se Harmonia já determina o que aquele usuário pode executar, a solução pode ser simplesmente alterar a superfície apresentada ao usuário. A capacidade existente, combinada com outra capacidade, resolve o problema.

Esse é o nível em que eu entregaria as instruções aos desenvolvedores agora.

E há uma consequência conceitual importante: o objetivo técnico não deve ser “fazer a Lyra parecer inteligente”. Deve ser fazer o ciclo inteiro funcionar. A inteligência é apenas a camada de decisão dentro desse organismo operacional.
